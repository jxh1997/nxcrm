## 服务器部署

### 1. 准备服务器

准备与安装教程匹配的 PHP、扩展、Composer、MySQL，以及 Nginx / PHP-FPM。以下假设项目路径为 `/srv/nxcrm`，PHP-FPM 运行用户为 `www-data`。

首次部署先完成[全新安装](安装教程.md#全新安装)，使用独立空数据库。在完成后台初始化、修改默认账号密码前，限制站点只向运维人员开放。

### 2. 配置生产环境

生产 `.env` 主要差异：

```dotenv
APP_ENV=production
APP_DEBUG=false
APP_URL=https://crm.example.com
ADMIN_HTTPS=true
CACHE_DRIVER=file
SESSION_DRIVER=file
QUEUE_CONNECTION=sync
```

`crm.example.com` 是占位域名，替换为真实地址。保留该环境原有 `APP_KEY`，填写真实数据库连接信息，使用 HTTPS 后再启用 `ADMIN_HTTPS`。有反向代理时还应核查可信代理配置，保证协议识别及 Cookie 行为正确。

安装生产依赖并刷新缓存：

```bash
cd /srv/nxcrm
composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction
composer check-platform-reqs --no-dev
php artisan optimize:clear
php artisan storage:link
php artisan config:cache
php artisan view:cache
```

`storage:link` 提示链接已存在时，先检查目标是否正确，不需要反复删除重建。后续修改 `.env` 后重建配置缓存，并重启长驻进程。

`APP_DEBUG=false`、运行目录指向 `public`、缓存配置等原则可核对 [Laravel 官方部署说明](https://laravel.com/docs/10.x/deployment)。

### 3. 配置目录权限

按服务器实际运行用户调整，例如：

```bash
sudo chown -R www-data:www-data storage bootstrap/cache
sudo chmod -R u+rwX,g+rwX storage bootstrap/cache
```

部署用户及调度 / 队列用户需要与 PHP-FPM 协调这些目录的访问权限。应用代码及 `.env` 只需对运行用户可读；`.env` 不应对其他用户开放。不使用 `chmod -R 777` 作为日常权限方案。

### 4. Nginx 配置

以下是未接入 TLS 前的 HTTP 验收模板；正式对外使用时在同一站点配置有效证书、443 监听，并将 HTTP 跳转到 HTTPS。

```nginx
server {
    listen 80;
    server_name crm.example.com;
    root /srv/nxcrm/public;
    index index.php;
    charset utf-8;
    client_max_body_size 20m;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location = /install.php {
        return 404;
    }

    location = /index.php {
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $realpath_root/index.php;
        fastcgi_pass unix:/run/php/php8.2-fpm.sock;
    }

    location ~ \.php$ {
        return 404;
    }

    location ~ /\.(?!well-known).* {
        deny all;
    }
}
```

使用实际 PHP-FPM Socket 替换示例。仅允许 `index.php` 执行，禁止旧安装入口和其他 PHP 文件。网站根目录必须为项目的 `public`，上传存储的公开访问属性见使用教程。

```bash
sudo nginx -t
sudo systemctl reload nginx
```

上面服务命令适用于 systemd Linux；其他系统按服务管理方式调整。同步检查 PHP 的 `upload_max_filesize`、`post_max_size`，后者应大于单文件限制；业务表单可能另有更小的限制。

### 5. 上线验收

- 登录页和后台首页正常，HTTP / HTTPS 跳转正确。
- 管理员及示例账号密码已经处理；员工账号权限验证通过。
- 能新增测试客户、合同、收款，并正确读取附件。
- `.env`、旧 `/install.php` 和非入口 PHP 文件不能通过网站访问。
- 定时任务设置已保存，调度可列出，运行日志可写。
- 已建立数据库、文件及密钥备份，完成一次隔离恢复验证。

生产服务由 Nginx / PHP-FPM 提供，不使用 `php artisan serve` 承载对外业务。

## 定时任务

项目调度在 `app/Console/Kernel.php`：公海回收每天执行；合同到期通知按后台保存的 `weekly` / `monthly` 执行。应用时区配置为 `PRC`。

先登录后台 `/admin/settings/reminder`，保存通知时间和双方通知方式，再检查：

```bash
php artisan schedule:list
```

全新安装未保存设置时，会出现 `Undefined array key "contract_day"`。这是当前代码依赖后台配置的表现；先完成设置再启用 cron。

为具有目录访问权限的运行用户添加一条 cron。替换项目路径和 PHP 路径：

```cron
* * * * * cd /srv/nxcrm && /usr/bin/php artisan schedule:run >> /srv/nxcrm/storage/logs/scheduler.log 2>&1
```

每分钟触发调度，由 Laravel 判断当前哪些任务到期。调度只需在一处配置，避免重复执行。配置方式见 [Laravel 调度文档](https://laravel.com/docs/10.x/scheduling)。

本地调试可在单独终端执行 `php artisan schedule:work`，停止时按 `Ctrl+C`。这个命令可能触发真实公海回收或通知，使用测试数据及测试通知配置。

可单独运行的业务命令：

| 命令 | 实际作用 |
| --- | --- |
| `php artisan nxos:high-seas` | 将符合规则的线索 / 客户清除负责人并放入公海 |
| `php artisan nxos:contract-exp-notice` | 按后台设置发送合同到期通知，可能发送真实短信 |

二者都是业务操作，不作为只读健康检查。检查调度使用 `schedule:list`，查看执行记录使用日志。

## 可选异步队列

默认 `QUEUE_CONNECTION=sync`，无需后台 worker；导入随 HTTP 请求执行。只有需要异步处理时才启用队列。

### 使用数据库队列

当前仓库有 `failed_jobs` 迁移，没有 `jobs` 队列表迁移。先确认未添加过，再生成和执行：

```bash
php artisan queue:table
php artisan migrate
```

修改 `.env`：

```dotenv
QUEUE_CONNECTION=database
```

刷新配置后启动：

```bash
php artisan optimize:clear
php artisan queue:work --tries=1 --timeout=60
```

默认数据库队列 `retry_after=90` 秒，worker 超时时间应小于它；如果导入任务需要更长时间，两者需一起调整。当前导入不具备重复提交去重策略，失败重试前先检查实际入库记录。生产通过 systemd / Supervisor 守护 worker，并配置正确工作目录和运行用户。

查看失败任务使用 `php artisan queue:failed`；确认任务重试不会重复产生业务数据后，再使用 `queue:retry`。部署新代码后执行 `php artisan queue:restart`，并确认进程管理器重新拉起 worker。

### 使用 Redis / Horizon

仓库包含 Horizon 和 Predis。使用 Redis 时配置 `QUEUE_CONNECTION=redis`、`REDIS_CLIENT=predis` 以及真实 Redis 地址 / 密码，刷新配置，验证连接后运行 `php artisan horizon`。生产需要进程守护。

数据库队列使用普通 worker，Horizon 用于 Redis 队列；不要为同一个队列无意间启动多套消费者。未使用 Redis 时不需要安装或启动 Horizon。

## 备份与恢复

### 备份范围

一次可恢复备份至少包含：

- MySQL 数据库：客户、联系人、合同、收款、权限、后台设置等。
- `.env`：特别是原有 `APP_KEY`，以及连接配置。
- `storage/app/public`：上传附件、范本和生成文件。
- 对应版本的代码与 `composer.lock`，以及发布时使用的前端构建资源。

备份保存在访问受限的独立目录，定期复制到项目所在机器之外。数据库备份与附件备份应保持一致；需要严格一致时，暂停写入并停止仍在写入的队列 / 调度任务。

### 数据库逻辑备份示例

以下以当前本机端口为例，其他环境替换连接参数。密码通过交互输入，从本地 `.env` 查看后自行填写，不放进命令行参数。

```bash
umask 077
mkdir -p "$HOME/nxcrm-backups"
mysqldump -h 127.0.0.1 -P 3307 -u nxcrm -p \
  --single-transaction --no-tablespaces \
  --set-gtid-purged=OFF --default-character-set=utf8mb4 \
  nxcrm_local > "$HOME/nxcrm-backups/nxcrm-$(date +%Y%m%d-%H%M%S).sql"
```

确认退出状态成功，备份文件非空，再备份附件及配置：

```bash
tar -czf "$HOME/nxcrm-backups/nxcrm-files-$(date +%Y%m%d-%H%M%S).tar.gz" \
  .env storage/app/public composer.lock
```

不要直接复制运行中 `storage/app/mysql-local` 的数据文件作为数据库备份；使用逻辑导出或专门的 MySQL 一致性备份方案。

### 隔离恢复演练

1. 在独立环境准备相同版本代码、依赖及空数据库。
2. 用有权限的账号导入备份 SQL：`mysql -h 127.0.0.1 -P 3306 -u 恢复账号 -p 恢复数据库 < 备份.sql`。
3. 在隔离项目中恢复附件和配置，保留备份的 `APP_KEY`，将数据库连接、访问地址改为隔离环境。
4. 将邮件设为 `log`，停用真实短信及调度，避免恢复测试发送真实通知。
5. 执行 `php artisan optimize:clear`、`php artisan storage:link`，验证登录、记录数量、金额和附件。

不要在恢复后运行 `nxos:install`，否则会重置密钥和配置。恢复覆盖生产数据库前，应先保留当前状态备份，并制定明确回退步骤。

## 升级流程

### 先理解项目命令

| 命令 | 用途及影响 |
| --- | --- |
| `nxos:install` | 首次安装：更换密钥、迁移、重建初始配置、重置管理员密码 |
| `nxos:reset` | 仅把 `admin` 账号密码重置为 `admin`，也可能新建该账号 |
| `nxos:update` | 迁移后执行 `DatabaseSeeder`，重置菜单、权限、扩展及扩展历史，再清理视图 |
| `migrate` | 执行未执行的数据库迁移；具体数据影响需检查目标版本迁移内容 |

`DatabaseSeeder` 调用的四个 Seeder 都先删除对应表的数据再插入预设值。所以自定义菜单、权限或扩展配置可能被 `nxos:update` 覆盖；它不是通用的无损升级命令。

### 有业务数据的升级步骤

1. 在测试环境使用备份副本验证目标版本及迁移内容，确认菜单 / 权限变更方案。
2. 备份生产数据库、附件、`.env` 和当前发布版本；保留原 `APP_KEY`。
3. 安排维护窗口，暂停写入；`php artisan down` 可关闭 Web 入口，队列和调度需要单独暂停。
4. 发布审核过的目标版本，保留生产配置和上传目录，按锁文件安装依赖。
5. 按版本说明执行所需迁移；生产使用 `php artisan migrate --force`。`--force` 只跳过生产确认，不会消除迁移风险。
6. 若升级需要新的种子配置，先对比四个 Seeder，再选择合适的合并方案，不直接对自定义配置执行重置。
7. 清缓存、重建配置及视图缓存，重启 PHP-FPM 和队列进程。
8. 使用 `php artisan up` 恢复 Web 服务，恢复调度 / 队列并完成业务验收。

出现问题时按预定方案恢复代码、数据库及文件。数据库迁移不一定可逆，不把 `migrate:rollback` 当作所有升级的自动回退方式。

## 日常维护

| 检查项 | 方法 |
| --- | --- |
| 页面健康 | 请求登录页，使用测试账号检查首页及关键业务页面 |
| 迁移状态 | `php artisan migrate:status` |
| 调度配置 | `php artisan schedule:list`，并检查 cron 日志 |
| 应用错误 | `storage/logs/laravel.log` |
| 当前本机 Web / MySQL | `storage/app/local-server.log`、`storage/app/mysql-local/mysql.log` |
| 队列 | 检查 worker / Horizon 存活状态及 `queue:failed` |
| 磁盘与文件 | 检查上传空间、备份空间、目录权限，配置日志轮转 |
| 数据可恢复性 | 定期在隔离环境恢复并核对业务与附件 |

公开文档不包含当前数据库密码或应用密钥。分享故障日志前检查是否包含手机号、客户资料、连接参数或其他敏感内容。
